# Migrating to xr 4.5.0

`xr` 4.5.0 renames and removes a few command words, reads an argument made only of digits as a user ID, words a
validation refusal as a sentence with its rule's code beside it, and names a command in `xr schema` by the words you run
it with, printing that command's `data` by default instead of the whole response wrapper. Each of these breaks a script
written against 4.4 and earlier, and this guide maps each one to what replaces it. They ship in a minor release, and
every old command word with a replacement is refused, naming what replaces it.

## Commands

| 4.4                                            | 4.5                                                                     | Notes                                                     |
| ---------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| `xr broadcasts scheduled remove <ID>`          | `xr broadcasts scheduled cancel <ID>`                                   | the verb `xr calls scheduled cancel` uses                 |
| `xr broadcasts scheduled live <ID>`            | `xr -X POST /2/broadcasts/scheduled/<ID>/live`                          | X takes every schedule `xr` makes live at its start time  |
| `xr broadcasts scheduled add --manual-publish` | none                                                                    | the same for `update`                                     |
| `xr broadcasts sources rename <ID> <NAME>`     | `xr broadcasts sources update <ID> --name <NAME>`                       | the label is a flag, as in `xr lists update --name`       |
| `xr broadcasts chat send <ID> <TEXT>`          | `xr -X POST /2/broadcasts/<ID>/chat -d '{"text":"<TEXT>"}'`             | `--reply-to` is `"reply_to"` in the body                  |
| `xr broadcasts chat remove <ID> <MESSAGE_ID>`  | `xr -X DELETE /2/broadcasts/<ID>/chat/<MESSAGE_ID>`                     | raw mode sends it without asking first                    |
| `xr broadcasts chat mute <ID> <USERNAME>`      | `xr -X POST /2/broadcasts/<ID>/chat/mutes -d '{"user_id":"<USER_ID>"}'` | `--until` is `"end_at_ms"`, `--message` is `"message_id"` |
| `xr broadcasts chat unmute <ID> <USERNAME>`    | `xr -X DELETE /2/broadcasts/<ID>/chat/mutes/<USER_ID>`                  |                                                           |
| `xr follow 1234` for the account named `1234`  | `xr follow @1234`                                                       | an argument made only of digits is a user ID              |

`scheduled remove` and `sources rename` are refused as `unknown-command` at exit 2, with the new word in `suggestion`
and its help in `next_step`. `live` and the four `chat` words are refused the same way with no suggestion, and
`--manual-publish` as `invalid-args` at exit 2.

The four `chat` commands act in a running broadcast's chat, which `xr` leaves to raw mode, and
`xr broadcasts chat history` still reads one. `mute` and `unmute` take the account's numeric ID, which
`xr user <USERNAME>` prints as `data.id`, and `"end_at_ms"` is the time in milliseconds since the Unix epoch.

Every command that names one account, and `--of` on `following`, `followers`, `lists list`, `lists followed`, and
`lists memberships`, takes a handle (`@jack` or `jack`) or a numeric user ID. An all-digit argument is sent as a user ID
with no lookup, so a script that names an all-digit handle without `@` now acts on another account. Prefix the handle
with `@`.

## Error envelopes

An agent that branches on `reason` reads these refusals differently:

| Refusal                                               | 4.4                                        | 4.5                                                                          |
| ----------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------- |
| An input a validator rejects                          | `validation`, the rule's code in `message` | `validation`, the code in `rule`, the sentence for the rule in `message`     |
| The same input under `--dry-run`                      | the rule's code as `reason`                | `validation`, with the real run's `rule`, `message`, and `next_step`         |
| A handle X knows no account for                       | `validation` at exit 1                     | `not-found` at exit 4, the handle without its `@` in `account`               |
| A 200 that carries `errors` and no `data`             | `validation`                               | `not-found` (exit 4), `forbidden`, or `invalid-request`, by X's problem type |
| A media job X failed after processing                 | `validation`                               | `invalid-request`, with `media_id` and X's detail in `message`               |
| A raw-mode URL that is neither absolute nor a path    | `validation`                               | `invalid-url`                                                                |
| A raw request with no URL                             | `validation` at exit 1                     | `invalid-args` at exit 2                                                     |
| A confirmation or picker prompt that fails            | `validation`                               | `io`                                                                         |
| `xr webhooks listen --dry-run` with no signing secret | `no-signing-secret`                        | `auth-required`, as the real run answers                                     |

A validation refusal also carries `value`, the offending input as given, when its rule names one, as
`xr auth apps add 'bad name!'` does:

```json
{
  "exit_code": 1,
  "message": "An app name is one or more letters, digits, '_', '.', or '-'; bad name! is not one.",
  "next_step": {"action": "fix-input"},
  "reason": "validation",
  "rule": "invalid-app-name",
  "status": "error",
  "value": "bad name!"
}
```

## `xr schema`

| 4.4                                                | 4.5                                      | Notes                                                 |
| -------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------- |
| `xr schema webhooks-subscriptions-count`           | `xr schema webhooks subscriptions count` | the words `xr` and `xr help` take                     |
| `xr schema redirect-uri-get`                       | `xr schema auth apps redirect-uri get`   | the same for `redirect-uri-set`                       |
| `xr schema skill-install`, `skill-install-all`     | none                                     | no schema, as for `skill update`                      |
| `xr schema envelope`                               | `xr schema --envelope`                   | the positional is gone                                |
| `xr schema post \| jq '.properties.data'`          | `xr schema post \| jq '.properties'`     | the default is `data`, resolved                       |
| `xr schema post` for the full document             | `xr schema post --full`                  | the same bytes as `schema/responses/post.schema.json` |
| `xr schema --list \| awk '{print $1}'`             | `xr schema --list --output tsv`          | names hold spaces; read the `command` column          |
| `xr schema --all` keys such as `lists-members-add` | keys such as `lists members add`         | each value is the default view                        |

There is no alias window. An old name with a replacement is refused with `invalid-args` at exit 2, and its `next_step`
is `fix-input` with the invocation that works:

```json
{
  "command": "webhooks-subscriptions-count",
  "exit_code": 2,
  "next_step": {"action": "fix-input", "command": "xr schema webhooks subscriptions count"},
  "reason": "invalid-args",
  "status": "error"
}
```

A word that names no command is refused the way `xr help` refuses it: `unknown-command` at exit 2, with the nearest
command in `suggestion`. In 4.4 it was `validation` at exit 1.

### The default output

`xr schema <command>` prints the schema of the command's `data` with every reference resolved in place, and labels it:

- `command`: the command's words.
- `data_cardinality`: `object`, or `array` when `data` is a list. For an array the body describes one element, so
  `.properties` always lists the fields.
- `data_type`: the type's name.
- `common_schema`: `xr schema --common`, the shared wrapper (`includes`, `meta`, `errors`), on a command that answers
  with it.
- `data_nullable`: `true` when `data` may be null.

`jq '.properties.data'` on the new default prints `null` and exits 0, so a pipeline built on it fails silently rather
than with an error. Move it to `.properties`, or keep the old document with `--full`.

Code generators that read the whole response (`json-schema-to-typescript`, `datamodel-codegen`) take `--full`.
`xr schema <command> --path a.b` prints one node of `data`, and `xr schema --common --path includes.users` one node of
the wrapper.

### Committed schema files

Every file under `schema/responses/` is named by its command's words joined with `-`, and
`xr schema --list --output json` names each command's file. Against 4.4:

- `redirect-uri-get.schema.json` and `redirect-uri-set.schema.json` are now `auth-apps-redirect-uri-get.schema.json` and
  `auth-apps-redirect-uri-set.schema.json`.
- `broadcasts-scheduled-remove.schema.json` and `broadcasts-sources-rename.schema.json` follow their commands to
  `broadcasts-scheduled-cancel.schema.json` and `broadcasts-sources-update.schema.json`.
- `broadcasts-scheduled-live.schema.json`, `skill-install.schema.json`, and `skill-install-all.schema.json` are removed,
  and so are `broadcasts-chat-send`, `-remove`, `-mute`, and `-unmute`, with their commands.
- `broadcasts-sources-list`, `-get`, `-add`, `-update`, and `-remove` describe the shape X answers with: `data` holds
  the sources or the source itself, a source's fields are `region`, `stream_key`, and `created_at_ms`, and `remove`
  answers `{"deleted": true}`.
- `schema/output.schema.json` gains `rule`, `value`, `account`, `path`, and `known_properties` on the error envelope,
  and `response_schema` on the dry-run envelope.

The other files keep their names and content, and each new command adds its own.
