# Migrating to xurl 3.3.0

xurl 3.3.0 changes the shape of two JSON outputs. `xr auth status` and `xr auth apps list` wrap their array under an
`apps` key, and `xr skill update --all` answers with one aggregated envelope instead of a separate envelope per host.
Both breaks are in the CLI's structured output only.

There is no library break. `cargo semver-checks` reports a patch bump sufficient against 3.2.0, so a crate consumer that
pins `xurl` and never parses CLI JSON needs no changes. Text output (`--output text`, the default) is unchanged for
every command in this guide.

If you have scripts or agents that read `--output json` from either command, read on.

## Change table

| Command                     | 3.2                             | 3.3                                        | Fix                              |
| --------------------------- | ------------------------------- | ------------------------------------------ | -------------------------------- |
| `xr auth status`            | bare array                      | `{"status": "ok", "apps": [...]}`          | select `.apps[]`                 |
| `xr auth apps list`         | bare array                      | `{"status": "ok", "apps": [...]}`          | select `.apps[]`                 |
| `xr skill update --all`     | one envelope per host, streamed | one envelope with an `installations` array | select `.installations[]`        |
| `xr skill update --all`     | installed every known host      | refreshes installed hosts, skips the rest  | use `xr skill install --all`     |
| `xr skill update` envelopes | no `command_preview`            | `command_preview` present                  | none, additive                   |
| `xr skill update` failure   | `remove-failed: <os error>`     | `remove-failed`                            | match the prefix, not the string |

The entry objects inside both arrays are unchanged. Only the wrapper is new.

## `xr auth status` and `xr auth apps list`

Every other message-shaped `xr auth` verb already answered with an object carrying `status: "ok"`. These two answered
with a bare array, so an agent branching on `.status` covered the whole auth surface except here, where there was no
object to branch on.

Before (3.2), an empty store and a store with one app:

```console
$ xr --output json auth status
[]
$ xr --output json auth status
[
  {
    "bearer": true,
    "bearer_source": "store",
    "client_id_hint": "",
    "default": true,
    "name": "default",
    "oauth1": false,
    "oauth2_users": [],
    "redirect_uri": "http://localhost:8080/callback",
    "redirect_uri_source": "built-in-default"
  }
]
```

After (3.3):

```console
$ xr --output json auth status
{
  "apps": [],
  "status": "ok"
}
$ xr --output json auth status
{
  "apps": [
    {
      "bearer": true,
      "bearer_source": "store",
      "client_id_hint": "",
      "default": true,
      "name": "default",
      "oauth1": false,
      "oauth2_users": [],
      "redirect_uri": "http://localhost:8080/callback",
      "redirect_uri_source": "built-in-default"
    }
  ],
  "status": "ok"
}
```

An empty store now emits `"apps": []` inside the envelope rather than a bare `[]`, so a caller iterates the array
without a zero-app special case.

Update any selector that reached the array at the top level:

```bash
# 3.2
xr --output json auth status | jaq -r '.[] | select(.default) | .name'

# 3.3
xr --output json auth status | jaq -r '.apps[] | select(.default) | .name'
```

A selector that has to work against both releases needs a type guard rather than `//`. On a bare array, `.apps`
raises instead of returning null, so the alternative operator never fires:

```bash
xr --output json auth status \
  | jaq -r '(if type == "object" then .apps else . end)[] | select(.default) | .name'
```

`xr auth apps list` takes the same wrapper and the same fix. The committed response schemas under
`schema/responses/auth-status.schema.json` and `auth-apps-list.schema.json` describe the entry objects, which did not
change.

## `xr skill update --all`

Two things changed here, and the behavior change matters more than the shape.

### It no longer installs where nothing is installed

In 3.2, `--all` ran the remove-and-reinstall pipeline against every known host, so it created an installation for every
host you had never installed to. That duplicated `xr skill install --all` and contradicted the verb. In 3.3, `--all`
refreshes the hosts that already have a destination and reports the rest as skipped.

If you were relying on `xr skill update --all` to install everywhere, use `xr skill install --all`, which is the verb
that does that.

### It answers with one envelope

`xr skill install --all` already aggregated into a single envelope carrying an `installations` array. `update --all`
emitted a separate envelope per host, concatenated, which is not one parseable JSON document. Both verbs now share the
aggregate shape.

Before (3.2), one object per host, streamed:

```console
$ xr --output json skill update --all --dry-run
{
  "action": "skill-update",
  "destination_status": "absent",
  "exit_code": 0,
  "host": "claude_code",
  "install_dir": "/home/you/.claude/skills/xurl-rs",
  "status": "dry_run",
  "would_succeed": true
}
{
  "action": "skill-update",
  "destination_status": "absent",
  "exit_code": 0,
  "host": "codex",
  ...
}
```

After (3.3), one document:

```console
$ xr --output json skill update --all --dry-run
{
  "action": "skill-update",
  "status": "dry_run",
  "exit_code": 0,
  "installations": [
    {
      "action": "skill-update",
      "host": "claude_code",
      "install_dir": "/home/you/.claude/skills/xurl-rs",
      "command_preview": "git clone --depth 1 https://github.com/brettdavies/xurl-rs-skill.git /home/you/.claude/skills/xurl-rs",
      "destination_status": "absent",
      "status": "skipped",
      "exit_code": 0,
      "reason": "not-installed"
    }
  ]
}
```

Update selectors accordingly, and expect `status: "skipped"` with `reason: "not-installed"` on a host that has nothing
installed. A skipped host carries `exit_code: 0`: no installation is not a failure, and the aggregate `exit_code` is the
worst observed across the array.

```bash
# 3.2, reading a stream
xr --output json skill update --all | jaq -s -r '.[] | select(.status == "error") | .host'

# 3.3, reading one document
xr --output json skill update --all | jaq -r '.installations[] | select(.status == "error") | .host'
```

Single-host `xr skill update <host>` keeps emitting one envelope, so a selector reading that is unaffected by the
wrapper. It does gain `command_preview` (below).

### Envelope field changes

Update envelopes now carry `command_preview`, matching what install envelopes have always reported. This is additive.

A failed destination removal now reports `reason: "remove-failed"` on its own. In 3.2 it appended the operating-system
error text, producing values like `remove-failed: Permission denied (os error 13)`. The reason set is meant to be a
closed vocabulary an agent can branch on, so the variable tail is gone. A matcher that compared the whole string needs
to match the prefix, or just compare equal to `remove-failed`.

## Unchanged

- Text output for every command in this guide, byte for byte.
- The entry objects inside `apps` and `installations`, field for field, apart from `command_preview`.
- Every other `xr auth` verb's envelope: they already carried `status: "ok"` as of 3.2.
- `xr skill install` and `xr skill install --all`, both shape and behavior.
- Single-host `xr skill update <host>` output shape, apart from the added `command_preview`.
- Exit codes, the error-envelope contract (`reason`, `exit_code`, `message`, `next_step`), and the `--output` format
  list.
- The public Rust library surface. `cargo semver-checks` reports patch-sufficient against 3.2.0.
